# Terraform example

A complete, self-contained configuration for banto: `terraform init -backend=false`
and `terraform validate` both pass on it as committed, with every value that
would otherwise need to pre-exist replaced by something Terraform creates or
an obviously fake placeholder. The main [README](../../README.md)'s own
Terraform excerpt, under "Deploying", is intentionally partial — it assumes
secrets and worker pools already exist. This does not: it creates everything
banto needs, plus one worker pool for it to manage, so applying it demonstrates
the whole loop end to end. It is still an example, not a module — read it
before you apply it, the same way you would read anything else you're about
to run in your own project.

## What this creates

| File | Resources |
| --- | --- |
| `registry.tf` | An Artifact Registry remote repository that proxies `ghcr.io`, because Cloud Run's v2 API cannot pull from it directly |
| `iam.tf` | banto's service account, the scheduler's service account, the runner pool's service account, the `workerPoolScaler` custom role, and the bindings that connect them |
| `state.tf` | The GCS bucket banto uses as its demand store |
| `secrets.tf` | The two Secret Manager secrets banto mounts, bootstrapped with placeholder versions (see below) |
| `service.tf` | The Cloud Run service running banto itself |
| `worker_pool.tf` | The one worker pool this example gives banto to manage, staffed by `var.runner_image` |
| `scheduler.tf` | The Cloud Scheduler job that calls `/reconcile` every five minutes |
| `outputs.tf` | The service URL, the worker pool name, and a couple of other values you'll want after applying |

Every resource here corresponds to something the main README explains — the
comments point back at the section, rather than repeating the reasoning.

## What to change first

Five things, in `variables.tf`:

1. `project_id` and `region` — a real project (id, not number — see the
   `BANTO_POOLS` notes in the main README) and region.
2. `github_org` / `github_repos` — the org and repositories this deployment
   should actually watch.
3. `gh_app_id` / `gh_app_installation_id` — from a real GitHub App and
   installation (see "Pointing a GitHub App at it" in the main README for how
   to create one).
4. The two secrets in `secrets.tf` — see the next section.
5. `runner_image` — an image that registers itself as a self-hosted GitHub
   Actions runner. See "The runner image" below.

Everything else — the bucket name, the custom role, the scheduler, the
Artifact Registry proxy — follows from those and shouldn't need touching.

## The two things Terraform cannot create for you

**The webhook secret and the GitHub App's private key.** You choose the
former; GitHub generates the latter and hands you a PEM when you create the
App. Neither can originate in Terraform, so `secrets.tf` creates the Secret
Manager *containers* and bootstraps each with a placeholder version —
`lifecycle.ignore_changes` on `secret_data` means Terraform creates that
version once and then never touches it again, so replacing it by hand doesn't
get undone on the next `apply`:

```sh
echo -n "a real webhook secret" | gcloud secrets versions add banto-webhook-secret --data-file=-
gcloud secrets versions add banto-gh-app-key --data-file=/path/to/the-app.private-key.pem
```

The placeholder for `GH_APP_PRIVATE_KEY` is generated by `tls_private_key` in
`secrets.tf` when you apply, rather than shipped in this repository. It exists
so the first `apply` produces a running, healthy service: banto's startup check
only verifies that the PEM parses (see `src/config.ts`), not that it
authenticates as anything, so `/healthz` comes up green before you've talked to
GitHub at all. It will not authenticate as your App until you replace it.

Generating it rather than committing one is deliberate. A private key in a
public repository trips secret scanning and push protection, and "it's only a
throwaway" is not a distinction those tools make — nor one a reader skimming
the file would make. The generated key lives in Terraform state, which is
where your real one sits between `gcloud secrets versions add` calls anyway.

**The runner image.** `var.runner_image` defaults to a placeholder path.
Neither banto nor this example builds a GitHub Actions runner image — that's
a separate concern this repository doesn't own. What `worker_pool.tf` needs is
any container that registers itself as an ephemeral, self-hosted runner
against `var.github_org` (or a `runnerRepo`, if you change `locals.tf` to set
one) and exits after one job; see "Known limitations" in the main README for
why one runner per instance matters. Point `runner_image` at your own build.

## After `terraform apply`

1. Add the real secret versions (above).
2. Create the GitHub App, following "Pointing a GitHub App at it" in the main
   README — its Webhook URL is `${output.banto_url}/webhook`.
3. Install the App on `var.github_org` (or just the repositories in
   `var.github_repos`), and confirm the installation id matches
   `var.gh_app_installation_id`.
4. Watch `gcloud run services logs read banto` for the structured
   `"scaling decision"` lines described under "Observability" in the main
   README once a workflow_job event arrives.

Until step 1 is done, banto starts and answers `/healthz`, but every webhook
delivery fails signature verification and `/reconcile` never authenticates
against a real GitHub App — an intentionally narrow gap between "the
infrastructure exists" and "banto is doing its job", which is the one this
example cannot close for you.

## What this example does not do

- It does not pick between the custom role and `roles/run.developer` for you
  — see the comment in `iam.tf`. The custom role is the default because it's
  the narrower grant, but it needs `iam.roles.create` on the project, which
  not every identity running `terraform apply` has.
- It does not grant `roles/iam.serviceAccountUser` on the runner's service
  account — see the same file for why, and when you'd add it.
- It leaves `deletion_protection = false` on both the service and the worker
  pool, and `force_destroy = true` on the bucket, so you can `terraform
  destroy` this while trying it out. Flip those before this is a real
  deployment.
- It scales one pool, with one label set, on one installation. The main
  README's own `BANTO_POOLS` example (under "Configuration") shows three
  pools with different `cooldownSeconds` and a `runnerRepo` — extend
  `locals.tf` the same way once one pool isn't enough.
